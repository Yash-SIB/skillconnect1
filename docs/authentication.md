# SkillConnect authentication

The sign-in page is at `/login`. The Google button is disabled, the callback route is absent, and no credentials or services are needed to build or run the app. The **Open Workspace Preview** link appears only in development. The workspace at `/` uses fictional data and must be protected before it can serve employee data.

## Recommended integration

Use the maintained **Better Auth** Google provider in the Next.js App Router. Next.js acts as the browser-facing authentication service, and PostgreSQL stores approved identities and revocable sessions. The Go service owns application authorization. Install and pin a patched stable Better Auth release when activating the flow, and verify it against the installed Next.js version. [Next.js integration](https://better-auth.com/docs/integrations/next) · [Google provider](https://better-auth.com/docs/authentication/google) · [Release history](https://better-auth.com/changelog)

1. Start Google OIDC from `/login` with a same-origin sign-in request. Use the authorization-code flow with library-managed state and S256 PKCE. Request `openid email profile` for identity and display only. Disable direct client-supplied ID-token sign-in and use a fixed post-login path or a same-origin allowlist.
2. Mount the library handler at `/api/auth/[...all]` once the employee gate is implemented. Have the server exchange the authorization code, then require verified Google ID-token claims before looking up any employee. Verify the signature with Google's trusted JWKS, issuer, client ID audience, expiry, and nonce when sent. Confirm that the pinned provider performs these checks on the actual callback path and supply a supported server-side verifier for any missing checks. Use the verified `sub` as the Google identity, require `email_verified === true`, and read the organization from the signed `hd` claim. The request's `hd` parameter is a Google account-picker hint. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
3. Require an administrator-confirmed hosted domain and a matching, active employee approval keyed by canonical Google issuer and subject. Pre-provision the account mapping to an internal employee ID in an administrator-controlled process. An approved email may help administrators match records, but a matching email or domain alone never grants access. Disable self-sign-up and automatic account linking. Missing claims, missing policy, missing or disabled approvals, and lookup failures must prevent session creation. Apply the same gate to returning users. Better Auth database hooks can gate session creation in addition to identity validation in the callback. [Provider configuration](https://better-auth.com/docs/reference/options) · [Database hooks](https://better-auth.com/docs/concepts/database#database-hooks)
4. Issue an opaque, host-only session cookie backed by PostgreSQL. Use `HttpOnly`, `SameSite=Lax`, and `Secure` over HTTPS. Keep cookie session caching disabled for revocation, cap session lifetime, and enforce expiry server-side. Revoke session records on logout and offboarding, and recheck employee status when resolving a session. Keep Better Auth's origin and CSRF checks enabled. Google tokens must stay server-side and be discarded unless required by a reviewed feature. Keep OAuth codes, tokens, secrets, and identity details out of logs. [Session management](https://better-auth.com/docs/concepts/session-management) · [Security defaults](https://better-auth.com/docs/reference/security)
5. Verify sessions near protected reads and mutations on every request. With this app's Cache Components setting, read the session in a request-time server boundary, never in a shared cache or prerendered private payload. Workspace membership and roles remain separate from authentication.

## Future Next.js → Go trust boundary

The frontend now has a live entry point at `/workspace` and a separate demo at `/`. The live entry point stops at a configuration-pending screen. During activation, render the live workspace from a server-verified Better Auth session and a workspace selected from the employee's approved memberships. Use request-time authorization and keep that bootstrap out of shared caches.

- For REST, the browser sends only its Next.js session cookie to the same-origin application. Next.js validates the session and employee approval, strips incoming identity headers and credentials, and calls the private Go API over TLS with a short-lived assertion signed by the SkillConnect service. The assertion contains the internal employee ID as `sub`, session ID for revocation checks, fixed issuer and Go-specific audience, issue time and expiry. Start with a 60-second maximum lifetime. Keep the signing key separate from the cookie secret and publish or distribute only verification keys to Go.
- Implement a same-origin Next.js gateway for the five `/api/v1` messaging routes. Recheck the session on each call, enforce a configured origin and CSRF protection for cookie-authenticated POSTs, and allowlist methods and upstream paths. Use a server-only Go origin, strip browser-supplied identity headers and cookies before forwarding, and return uncached responses. Do not add credentialed cross-origin browser access. The current client reserves these paths without exposing a forwarding route or storing a service assertion in the browser.
- Go verifies the signature against a configured trusted key set, pins the algorithm, checks token type, issuer, audience and timestamps, and resolves `sub` and the session against trusted records or internal introspection. Go enforces current employee status, workspace membership and conversation permissions on every read and write. Browser-supplied IDs, emails and roles, Google tokens, and Next.js cookies are outside this API's trust boundary. [JWT Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html)
- For WebSockets, use a same-origin upgrade gateway that validates the request origin and the session, then forwards a trusted server assertion to Go. Go checks authorization at subscription and mutation time and terminates connections on session expiry or revocation. Avoid putting reusable credentials in WebSocket URLs.
- The browser client takes a gateway-readiness value only from the server-controlled workspace bootstrap. Keep it pending until the verified session, Origin check, and trusted upgrade are in place. Each permitted browser reconnect must obtain a fresh upstream assertion through the gateway. The client stops on a Go policy close because the same code covers both expiry and revoked access. Define how the gateway revalidates and renews an expiring session before enabling automatic expiry recovery.

## Google Cloud Console setup

Use a Skillinabox-owned **development** Google Cloud project and have the Workspace administrator confirm the allowed hosted domain or domains. Setting up the Cloud client can be done separately from deploying any code.

1. Open **Google Auth platform → Branding**. Create the OAuth configuration with **SkillConnect** as the app name and the team's approved support email and developer contacts.
2. In **Audience**, choose **Internal** in the Skillinabox Google Workspace organization. If Internal is unavailable, confirm project ownership with the administrator before proceeding. Keep the employee approval check even for an Internal audience.
3. Under **Data Access**, request only the identity scopes `openid`, `https://www.googleapis.com/auth/userinfo.email` and `https://www.googleapis.com/auth/userinfo.profile`. Calendar and Drive permissions belong to a separate future consent flow.
4. In **Clients → Create client**, choose **Web application**, name it **SkillConnect Local**, and add exactly `http://localhost:3000/api/auth/callback/google` under **Authorized redirect URIs**. This server-side flow does not need an authorized JavaScript origin. Use `localhost` consistently when testing. Use a separate client and an exact HTTPS callback for each hosted environment. [Google OAuth configuration](https://developers.google.com/workspace/marketplace/configure-oauth-consent-screen) · [OAuth clients](https://developers.google.com/workspace/guides/create-credentials)
5. When implementing activation, copy the template into the Next.js app directory. Use an ignored local file for development and the deployment secret store for hosted environments.

   ```powershell
   Copy-Item apps/web/.env.example apps/web/.env.local
   node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"
   ```

   Run the copy once for a new local setup. Put the generated value in `BETTER_AUTH_SECRET`, the development credentials in `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, the confirmed domains in `SKILLCONNECT_GOOGLE_HOSTED_DOMAINS`, and the local database connection in `DATABASE_URL`. Keep `BETTER_AUTH_URL=http://localhost:3000`. Treat the generated value as a secret and keep all variables server-side.
6. Implement the provider callback, employee gate, database migration, session lookup and protected page before enabling the button. Seed individually approved test accounts. Verify approved sign-in, same-domain rejection for an unapproved account, wrong-domain rejection, state and token validation failures, and logout and offboarding revocation. Then run `npm.cmd run dev` and test through `http://localhost:3000/login`. Filling the environment file alone leaves this scaffold inactive.
